编译器与编译优化等级不同，rom 开销可能不同。

## 调度器 ltx

- ram：72 Byte
- rom: 618 Byte

## 协程管理 ctx

- ram：约 108 Byte（不含动态内存池的情况）
- rom: 622 Byte

## 单个协程

- 协程控制块 (struct coro_stu): 84 Byte
- 协程帧（保存参数、局部变量和返回值的结构体）: 可自定义可静态分配，对象池单个块默认设置为 100 Byte
- 任务栈：无。无栈协程设计，所有任务共用主栈，出让后不需要保存栈，出让恢复点保存在协程控制块内。

## 动态分配耗时

使用固定大小的对象池进行分配，通过 freelist 实现。  
分配与释放内存块只需要几条指令，耗时极低。

## 协程状态机额外 rom 开销

指翻译后的函数与翻译前的函数的 rom 差值。不知道怎么算，应该不会增加太多，本身手写状态机或者回调也要消耗差不多空间，所以应该不用考虑这个。

## 组件开销

在使用 `_await` 或 `_await_static` 异步等待被调用函数时，通常都会需要创建被调用函数的协程对象，对于内嵌组件，即便使用异步关键字调用，也不会有额外的协程对象创建开销，因为它们都只是对调用者的定时器和订阅器的操作的封装，例如 `delay_ticks` 就是修改调用者的内部定时器的倒计时然后出让，而 `wait_topic` 则是在 `ctx.c` 内部通过全局变量静态创建了一个对象，这个对象是所有任务共用的，甚至 `mutex` 组件的等待事件也用了这部分内存，ctx 的 ram 开销基本上就体现在这里。  

部分拓展组件需要在使用时创建额外的协程对象，会带来一点内存分配开销。

**ctx 内嵌组件：**
* delay_ticks：
  * **不需要** 动态或静态创建额外协程对象进行事件等待
* wait_topic：
  * **不需要** 动态或静态创建 额外 协程对象进行事件等待


**ctx 可选组件：**
* events：
  * ram：0 Byte
  * rom：xxx Bytes
  * **需要** 动态或静态创建额外协程对象进行事件等待
* mutex：
  * ram：0 Byte
  * rom：xxx Bytes
  * **不需要** 动态或静态创建额外协程对象进行事件等待
